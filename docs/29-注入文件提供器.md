# 注入文件提供器（DocumentsProvider）

> 适用：要改「设置 → 存储与工具 → 注入文件提供器」、排查「MT 管理器里看不到本应用 / 打开是空的」、或想给别的应用加同类能力。

## 这是什么

让第三方文件管理器（典型：MT 管理器）在**无需 ROOT** 的情况下浏览本应用的私有目录。实现方式是系统标准的 SAF（Storage Access Framework）`DocumentsProvider`，不是私有的兼容层。

开启后 MT 管理器「添加本地存储」里会出现本应用，进去有四个入口：

| 入口 | 实际路径 | 内容 |
|---|---|---|
| `data` | `/data/user/0/<包名>` | files / cache / databases / shared_prefs |
| `android_data` | `/sdcard/Android/data/<包名>` | 外置私有目录 |
| `android_obb` | `/sdcard/Android/obb/<包名>` | 仅目录存在时挂载 |
| `user_de_data` | `/data/user_de/0/<包名>` | 设备加密存储，仅存在时挂载 |

## 为什么默认关闭

`data` 里有 `cookies/{host}/{account}` 与账号设置。provider 一旦常驻，**任何能拉起系统文件选择器的应用**都能诱导用户点一下授权就读到它。所以：

- 原生两个组件（provider + 唤醒 Activity）都写死 `android:enabled="false"`；
- 只有用户在本应用的设置里主动打开，才由 `AppDataFilesBridge` 调 `setComponentEnabledSetting` 启用；
- 设置项默认值是 `false`（`StorageSettings.docProviderEnabled`）。

这不是「以后再补的安全加固」，而是当前设计的一部分 —— **改 Manifest 时不要顺手把 enabled 改成 true 或删掉**。

## 安全边界在哪

靠 `android:permission="android.permission.MANAGE_DOCUMENTS"`。这是 signature 级权限，只有系统（DocumentsUI / Settings）持有。第三方应用不能直接 `query` 本 provider，必须由用户在系统选择器里选中本应用、拿到系统授予的 URI 权限后才能访问 —— 与 SAF 标准模型一致。

不要为了「方便调试」去掉这个属性。调试时想看 provider 是否正常，用 root shell 直接查（见下），那是另一条路。

## 关键实现点

| 文件 | 职责 |
|---|---|
| `android/app/src/main/kotlin/com/github/hlnm/mt/discuz/AppDataFilesProvider.kt` | `DocumentsProvider` 实现：四个挂载点、增删改查、MT 扩展方法 |
| `android/app/src/main/kotlin/com/github/hlnm/mt/discuz/AppDataFilesWakeUpActivity.kt` | 空 Activity，仅用于把进程拉起来 |
| `android/app/src/main/kotlin/com/github/hlnm/mt/discuz/AppDataFilesBridge.kt` | MethodChannel 开关，`setComponentEnabledSetting(DONT_KILL_APP)` |
| `lib/core/app/app_data_files.dart` | Dart 侧唯一边界；非 Android 恒为不可用 |
| `lib/pages/settings/models/data_settings.dart` | 设置项（`SwitchSetting`，值来自 `SettingsProvider.docProviderEnabled`） |

几处**不能改**的细节：

1. **存在性判断用 `Os.lstat` 而不是 `File.exists()`**。软链接指向不可访问的目标时 `exists()` 返回 `false`，会把链接整个藏掉；应用目录里确实会有这种残留链接。
2. **递归删除先判软链接**。`deleteRecursively` 先 `lstat` 判断是不是链接，是链接就只删链接本身 —— 否则会把链接目标（可能在 `data` 之外）一起删掉。
3. **`mt_extras` 列格式 `mode|uid|gid[|readlink]`**。这是 MT 的私有协议，改了 MT 里「权限 / 所有者」就显示不出来。
4. **`mt:*` 方法名沿用 MT 的定义**（`mt:setLastModified` / `mt:setPermissions` / `mt:createSymlink`），否则 MT 对应菜单直接灰掉。
5. **`getParcelable(String)` 保持弃用重载**。带 ClassLoader 的新重载在 API 33 以下不存在，minSdk 覆盖低版本时调用会 `NoSuchMethodError`；已有 `@Suppress("DEPRECATION")`，不要「顺手修掉」。
6. **开关只走 `applyRuntimeConfig()` 一条路径**。设置页改值、导入设置覆盖、启动加载，最终都经过它；在那里 `unawaited(AppDataFiles.sync(...))` 把原生组件状态对齐一次（先读再写，已是目标值就不写）。散在各处 `onChanged` 里直接调原生，会漏掉「导入设置」这条路径。

## 唤醒 Activity 为什么必须存在

provider 跑在本应用进程里。进程被系统回收后，第三方来查会拿到 "provider not found"。MT 在查询前会先尝试启动一个约定的 Activity 把进程拉起来，所以必须留一个空实现（`onCreate` 里立刻 `finish()`），并配 `excludeFromRecents` + `noHistory`，否则会在最近任务里闪一下。

它和 provider 是**一对**：`AppDataFilesBridge` 同时启停两者。只开 provider 的话，冷查询仍然会失败。

## 调试

用 root shell 直接查（绕过 MANAGE_DOCUMENTS 限制，验证 provider 本身是否正常）：

```bash
am start -n com.github.hlnm.mt.discuz/.AppDataFilesWakeUpActivity   # 先把进程拉起来
content query --uri content://com.github.hlnm.mt.discuz.MTDataFilesProvider/
```

- 正式包 authorities 是 `com.github.hlnm.mt.discuz.MTDataFilesProvider`；
- debug / beta 变体分别带 `.debug` / `.beta` 后缀（`${applicationId}` 前缀），互不冲突。

界面上的验证路径：MT 管理器 → 侧拉栏 →「添加本地存储」→ 找到本应用 → 选择。

## 参考实现与取舍

思路对齐 MT 作者林锦斌的 [MTDataFilesProvider](https://github.com/L-JINBIN/MTDataFilesProvider) 与 [PiliPlus](https://github.com/bggRGjQaUbCoE/PiliPlus)（`BiliDocumentsProvider`）。两者授权情况不同：

- `PiliPlus` 是 GPL-3.0，与本项目一致；
- `MTDataFilesProvider` **没有 LICENSE 文件**（无授权即保留所有权利），因此**不复制其代码**。

代码为本项目自行实现，只对齐协议常量（入口名、`mt:*` 方法名、`mt_extras` 格式）以保证 MT 侧功能完整。从 PiliPlus 采纳了两点：`Root.FLAG_LOCAL_ONLY`、以及文档标志位补 `FLAG_SUPPORTS_MOVE` / `FLAG_SUPPORTS_REMOVE`（否则 MT 的「移动 / 移除」是灰的）。

用 `setComponentEnabledSetting` 做运行时开关的思路也来自 PiliPlus；区别是它把开关放「其他设置」，本项目放「存储与工具」，与本项目设置分组的心智模型一致。
