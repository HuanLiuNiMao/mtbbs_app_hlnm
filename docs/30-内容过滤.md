# 内容过滤（板块名单 / 帖子与评论屏蔽）

> 适用：新增/修改「屏蔽」类能力、调整评论屏蔽的触发方式、排查「屏蔽没生效 / 误伤正常回复」。实现集中在 `lib/core/utils/content_filter.dart`，本文件只讲取舍与坑。

## 两套屏蔽，各自独立

| 能力 | 作用对象 | 配置形态 | 设置入口 |
|---|---|---|---|
| 帖子列表屏蔽 | 列表里的主题卡片（`ThreadItem`） | 每个列表点一份 `ThreadScopeFilter` | 「帖子列表屏蔽」二级页 |
| 评论屏蔽 | 楼层正文（`PostItem` / 裸 bbcode） | 全局一份 `CommentFilterConfig` | 「评论屏蔽」二级页 |
四个列表点是 `community` / `guide` / `search` / `user`（社区、导读、搜索、个人主页）。两者共用同一套**关键词匹配语义**（`CommentWordMatcher`：合法正则按正则、非法正则退化为子串、大小写不敏感）与同一个**板块名单语义**（`filterByBoard`：黑名单命中即隐藏、白名单未命中即隐藏）。

## 列表页右上角快捷入口

「我的帖子 / 最近回复 / Ta的帖子」（`/my-threads`，列表点 `user`）右上角有一个屏蔽图标，点开是
`showContentFilterQuickSheet`（`lib/pages/settings/content_filter_quick_sheet.dart`）：
帖子列表屏蔽的开关 + 「帖子列表屏蔽设置」入口；回帖列表（`type=reply`）额外多一组评论屏蔽的
开关 + 「评论屏蔽设置」入口。

**为什么是面板而不是「点图标直接切开关」。** 两层屏蔽互相独立（列表点一份、评论全局一份），
一键切换只能动其中一层，用户分不清关掉的是哪层；面板把开关和「去哪改细节」摆在同一处，
一次点击可达。图标本身用 `filter_alt` / `filter_alt_off` 表达「本页现在会不会隐藏内容」，
判定要按页面真正消费的层算：帖子列表页只看 `ThreadScopeFilter`，回帖列表页再加上
`CommentFilterConfig`——否则「帖子」页会因为评论屏蔽开着而显示成开启态，误导用户。

**列表点显示名只能有一份。** `threadScopeTitle(scope)`（`lib/core/utils/content_filter.dart`）
是唯一来源，设置页与快捷面板都调它。此前设置页自带一份 `_scopeTitles` 字面量，加一个入口就
多一处要同步的文案，改名必然漂移。

**回帖列表的楼层必须「存原文 + 渲染期过滤」。** 早期在拉取时就 `filterPostItems`，结果是用
户在面板里关掉屏蔽后，已展开的楼层仍是过滤后的旧列表，必须收起再展开才恢复。现在
`_expandedReplies` 存 `_ExpandedReply`（原始楼层 + `boardName` + `isHiddenThread`），
每次 build 用当前配置投影一次；因此页面读 `SettingsProvider` 必须 `watch`（同「配置必须
watch」那条）。「楼主帖去重」（`sublist(1)`）仍在存原文之前做——`authorid` 筛选下 `isOp` 全为
false，屏蔽的楼主豁免在这里不生效，首条只能靠 uid 对比去掉。

## 评论屏蔽的触发方式

`CommentFilterConfig` 有开关、两种触发方式、屏蔽词，**没有内置默认词表**（屏蔽词完全由用户维护，为空即不屏蔽任何评论）。另有一个显示层字段 `showBlockedPlaceholder`（默认 `false`），只管「消息 → 我的帖子」命中屏蔽后要不要留提示，见下文。

| 触发方式 | 字段 | 生效条件 |
|---|---|---|
| 不设置（默认） | — | 屏蔽词对所有主题生效（`isGlobalTrigger`） |
| 仅隐藏贴 | `onlyHiddenThread` | 当前主题是隐藏贴 |
| 分板块 | `boards` + `modeBlock` | 当前主题板块命中 `filterByBoard` |

两者是**或**关系：任一命中即应用屏蔽词。判定入口统一是 `commentFilterApplies(f, boardName:, isHiddenThread:)`，`filterPostItems` 与 `shouldBlockCommentBbcode` 都只调它，不要在各调用点自己写 `if`。

「隐藏贴」的判据是 `isHiddenThreadBbcode`：`[appdata]{"type":"locked"}`（未回复时的 🔒 占位）或 `[hide]...[/hide]` 块。两者都是解析层已产出的标记，**不需要额外请求**。locked 正则只在 `content_filter.dart` 维护一份（`kLockedAppdataRe`），帖子页「回复后重取主帖」也用它。

「分板块」需要当前主题的板块名。详情页拿不到 `ThreadItem.boardName`（那是列表页字段），所以 `ThreadViewData` 单独补了 `boardName`，由详情解析从面包屑（`parseBoardFields`）提取；解析不到时为空串，此时该触发条件视为**无法命中**（保守不屏蔽）。

## 三个消费点

| 位置 | 入口 | 上下文 |
|---|---|---|
| 帖子详情评论区 | `filterPostItems` | 有 `boardName` + `isHiddenThread` |
| 「我的帖子」展开回复 | `filterPostItems` | 同上（取自同一次详情结果） |
| 消息 → 我的帖子（回帖预览） | `shouldHideMypostEntry` / `isMypostEntryBlocked` | 只有单条 bbcode，**拿不到上下文** |

消息页默认把命中的提醒**整条从列表移除**（卡片、头像、「回复了您的帖子」、查看/回复按钮全都不渲染），只有用户打开「命中后保留提示」才保留整卡 + 一行提示代替正文。早期只把正文换成提示、卡片照旧留着，用户设了屏蔽词却仍看到消息在列表里，表现为「屏蔽没生效」——内容既已被主动屏蔽，整条提醒就没有存在意义。

消息页拿不到板块与隐藏贴标记，所以**不参与**触发方式判定（调 `withoutTrigger()`）：只要开关开着且有屏蔽词就过滤。若沿用触发方式，会被判为「无法命中」而永久不过滤，与「消息里也过滤」的需求相悖。触发方式是为浏览帖子时的评论区做精细控制用的。

**整条隐藏靠 `buildPagedList` 的 `itemVisible` 投影实现，不是先过滤数据再渲染。** `PagedListStateMixin` 的 `_previews` 缓存、`_previewLoading`、`_tryFetchPreview(index)` 全部以**原始下标**为 key；若把 `items` 本身过滤掉，下标会整体前移，预览就会错位到别的提醒上。所以 `itemVisible` 只决定「这条渲染不渲染」，`itemBuilder` 收到的仍是原始下标。改这块时不要为了「省一次判断」把数据源换成过滤后的列表。

**整页都被屏蔽时自动补页（限 3 次）。** 列表没有任何可滚动的行，触底加载更多不会触发，用户会卡在空白页上、后面几页的正常提醒永远看不到。判据是「隐藏条数 == 当前条目数」而不是「不足一页基准」——预览是逐条异步拉回来的，用基准条数会在预览还没回来时误判成整页被屏蔽，白白发请求。补页计数在 `onItemsReplaced`（重新加载 / 刷新）与 `onSubtypeChanged`（切子类型）时重置；`_autoExtendScheduled` 防止 build 连跑几次时重复排队。

**配置必须 `watch` 而不是 `read`。** `_body()` 里读 `SettingsProvider` 用 `context.watch`：用户改完屏蔽词返回列表时必须重新判定一遍，用 `read` 不会重建，旧结果留在屏幕上，同样表现为「过滤没生效」。

## 只看楼主（评论区筛选）

评论区头部的「只看楼主」是**筛选**，不是屏蔽，也不属于「内容过滤」配置的一部分：
它只作用于当前帖子页、不持久化、换帖子即复位。

| 关注点 | 做法 |
|---|---|
| 筛选入口 | `filterOnlyOpAuthor(posts, opUid)`（`lib/core/utils/content_filter.dart`） |
| 判定条件 | `p.isOp || p.uid == opUid`，`opUid` 为空则原样返回 |
| 主帖 | **照常显示**（只筛评论楼层） |

**为什么不用服务端 `authorid` 参数。** 页面本身支持 `authorid`（用于「只看某人的回复」深链），
但 `authorid` 非空时解析层会把第一楼也当成评论，返回结果里 `mainPost == null`，
页面上的主帖会整块消失。切换筛选时主帖忽隐忽现体验很差，而且每次切换都要重新请求。
客户端筛选没有这两个问题，代价是只作用于**已加载的页**——后面几页仍可能有楼主的回复，
所以筛空时文案要说「本页没有楼主的回复 / 可以翻到下一页看看」，不能写「暂无评论」。

**过滤顺序不能调。** 必须放在「评论屏蔽补页判定」**之后**：

```
屏蔽过滤 → 补页判定（用屏蔽后的可见量）→ 只看楼主过滤 → 渲染
```

若先按楼主筛，可见量天然远小于一页基准，会一直满足扩窗条件，白白多拉最多 5 页请求，
而扩来的页里绝大多数楼层仍会被筛掉。

**UI 取舍。** 评论区头部横向已排满（刷新 / 上一页 / 页码 / 下一页），且这行的
`SliverPersistentHeader` 固定 44 高——加不了行高。所以用**标题右侧 24 高的胶囊**，
而不是 `Switch`：胶囊只占一行、开启时主题色填充表示「正在筛选」，关闭时仅描边。
（`Switch` 尺寸至少 40×30，且这是筛选动作而非设置项，语义也不匹配。）

**胶囊必须放在有界宽度里。** 早期实现把它直接塞进头部 `Row`（配一个 `Spacer` 占剩余
空间），结果是胶囊拿到**无限宽约束**：内部 `Text` 的 `overflow: ellipsis` 永远不触发，
窄屏（320dp）下整行会 `RenderFlex overflow`。正确做法是把「图标 + 标题 + 胶囊」整体包进
一层 `Expanded`，内层 `Row` 才有确定宽度，胶囊再套 `Flexible` 兜底，极窄屏或大字体时
文字省略而不是报错。

**开启态文案不加后缀。** 曾用「只看楼主·开」表达状态，比关闭态多两个字，320dp 下整行
需求 310dp 而可用仅 296dp，直接溢出。状态改由**填充色 + 实心图标 + 加粗**三重表达，
文案始终是「只看楼主」——同宽度下信息量不降，还不占横向空间。

## 必须保留的不变量

- **判定链顺序**：去空白为空 → 不屏蔽；超过 10 字 → 不屏蔽；纯 ASCII 可打印且不含 `.` → 屏蔽；命中屏蔽词 → 屏蔽。这条链是用户已习惯的屏蔽强度，改它等于悄悄改变行为。
- **两条豁免**：楼主帖（`isOp`）与「回复别人」的楼层（带非提示类引用块）不屏蔽。引用块里是「回复可见」提示时不算回复别人，仍按正常规则判定。
- **「我的帖子」先去重再过滤**：`authorid` 筛选下 `isOp` 全为 false，首条是楼主帖、靠 uid 对比去重；若先过滤再 `sublist(1)`，首条被屏蔽后会把真实回复误删。顺序写在该文件注释里，不要调换。
- **补页判据**：过滤后可见条数不足一页基准时自动向后扩窗，判据用 `commentFilterApplies` 而不是裸开关——触发方式不命中的主题不该触发补页。

## 迁移与备份

评论屏蔽从「`commentFilterKeywords` + `commentBlockEnabled`」两个扁平键升级为一份 JSON（key = `commentFilter`）。加载时**只要旧键还在**就做一次幂等合并：`mergeLegacyKeywords(legacy, current)`（`lib/core/utils/content_filter.dart`）把旧词并进新配置——旧词在前、双向去重、trim 后丢弃空串、剔除以 `康康看下|` 开头的旧内置词行（那是被删除的内置词表合并成的正则，不剔除会表现为「内置词没删掉」）。合并完把三个旧键（含 `commentBlockWordsVersion`）删掉。

**判据必须是「旧键还在不在」，不能是「新键空不空」。** 旧实现把迁移包在 `else` 分支里，只在 `commentFilter` 为 null 或空串时才读旧键；一旦新键被写过（用户点开屏蔽页触发一次保存、或导入一份空备份），旧词就永远读不到，紧接着 `deleteSetting` 把旧键删掉 → 数据永久丢失。这就是「升级后屏蔽词消失」的完整因果链。改成幂等合并后，无论新键处于什么状态，旧键存在就能继承，重复执行也不会产生重复词。

备份键清单（`lib/services/backup/backup_collectors.dart`）只列 `commentFilter`，不再列旧键——否则恢复旧备份会把废弃键写回来，与迁移逻辑打架。

## 踩坑记录

**症状**：升级后内置屏蔽词仍在生效，用户删了也没用。
**根因**：旧版把 80 条内置词合并成一条 `|` 正则写进用户设置，那条数据属于用户设置而不属于代码常量，删常量不影响已升级的用户。
**修法**：迁移时按 `康康看下|` 前缀剔除该行（见 `settings_provider_persistence.dart`）。
**教训**：预置进用户数据的默认值，删除时必须同时写迁移；只删代码常量等于没删。

**症状**：升级后用户自加的屏蔽词全部消失（不是内置词残留，而是连用户自己加的词一起没了）。
**根因**：迁移的判据写成了「新键不存在」，而不是「旧键还在」。新键只要被写过一次（点开屏蔽页就会保存），迁移分支永久跳过，随后旧键被 `deleteSetting` 删除 → 旧词再也读不回来。
**修法**：判据改为 `legacyRaw != null`（旧键还在就继承），合并逻辑抽成纯函数 `mergeLegacyKeywords` 做幂等去重；`test/comment_filter_inherit_test.dart` 覆盖空旧键、双向去重、内置词剔除、连续合并幂等等 12 个用例。
**教训**：迁移的判据要看源数据还在不在，而不是目标数据有没有。目标数据可能被「一次无意义的保存」提前写出来，此时按「目标为空」判断就永远不会执行迁移。
