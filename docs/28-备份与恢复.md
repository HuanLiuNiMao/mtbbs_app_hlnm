# 备份与恢复（自定义备份项 / 本地备份 / Web 备份 / 运行日志）

> 适用：新增或修改备份项、排查「导出的包缺了什么」「导入后某项没生效」、接入 Web 备份服务器时读。按需。

## 一句话

备份从「一刀切导出全部设置」改为**可勾选的模块化备份包**：`BackupCatalog` 声明有哪些项，`BackupCollectors` 提供读/写实现，`BackupService` 按勾选裁剪并逐项记日志。**未勾选的项不进包，导入时也不动本机对应数据**——这是整套设计的核心保证。

## 备份项清单（当前 11 个叶子）

应用设置、站点设置、快捷方式、MT 图床上传历史、**浏览记录·用户**、**浏览记录·帖子**（两者归在 `browseHistory` 分组下，可整组勾选或单独勾选）、编辑框设置、编辑框草稿（依赖编辑框设置）、内容过滤、MCP 配置（敏感）、**账号列表**（依赖站点设置）、**Cookie**（敏感，依赖站点设置）。

勾选默认值：`defaultSelected: true` 的项在首次运行/重置时勾上；草稿、MCP、Cookie 默认不勾。

### 账号列表 vs Cookie（2026-11 拆分）

原本「账号与 Cookie」是一项。拆开的原因是两者的敏感度与使用场景不同：

| | `accountCookies` | `cookies` |
|---|---|---|
| 标题 | 账号列表 | Cookie |
| 包内键 | `account_cookies` | `cookies` |
| 内容 | `host` / `baseUrl` / `accounts`（UID、昵称、头像） | `host` / `baseUrl` / `cookies`（各账号的凭据罐） |
| 敏感 | 否 | 是（导入前二次确认） |
| 典型场景 | 换机后想看到「我登过哪些站、哪些号」但不想带凭据 | 只刷新登录态、不动账号列表 |

**两个 collector 都调 `DataPortability.exportCookiesJson()`，再各自剥掉不需要的字段**（`_collectAccountCookies` 剥 `cookies`，`_collectCookies` 剥 `accounts`）。这样「站点/账号口径」永远一致——各写一套遍历逻辑，早晚会因为过滤条件不同而错位（比如一边跳过 uid 为 0 的游客、另一边没跳）。导入同理，都走 `importCookiesJson`：payload 里没有 `cookies` 键就不动 Cookie 罐，没有 `accounts` 键就不动账号列表。

两边的格式都是 `mtbbs.cookies` v1，**所以 `cookies` 模块的 payload 单独抽出来就是上游的「导出账号 Cookie」文件**，可直接喂给上游 App；反之上游导出的文件也能直接当 `cookies` 模块导入。备份页的「账号 Cookie」区块就是把这个能力单独暴露成一个入口。

## 关键设计决策

- **枚举名冻结**：`BackupItemId` 的枚举名会写进 `AppSettings.backup.selected`，改名等价于用户丢勾选状态（回落默认值）。包内键名另由 `payloadKey` 定义，与枚举名解耦，所以「UI 名字」与「包内键名」可各自演进。
- **分组父不产生 payload**：`payloadKey == null` 即分组头，只用于 UI 聚合（全选/半选由子项推导）；写进包里的永远是叶子项。
- **依赖用 `requires` 表达，取消要级联**：勾草稿自动勾编辑框设置；取消编辑框设置会级联取消草稿（`BackupSelection.toggled` 里做）。漏了级联会出现「包里只有草稿、没编辑器设置」的半残状态。
- **导入有固定顺序**（`BackupCatalog.applyOrder`）：站点设置必须早于快捷方式与 Cookie（前者决定 host 是否存在、后者要 host 的 baseUrl）。顺序错的表现是「导入后快捷方式被清空」。
- **两份数据永不被包覆盖**：应用设置导入时强制保留本机 `currentSiteHost`（包里的站点在本机可能不存在，会导致启动落在空站点）与 `backup`（勾选状态本身，否则用户下次备份选项莫名变化）。
- **事务式导入靠「同一套 collector 拍快照」**：`BackupImportStrategy.atomic` 下失败按快照 `replace` 写回；快照本身失败的模块会在日志里标「不可回滚」，此时数据可能处于中间态——回滚失败会显式记 `e` 级日志。
- **Web 备份 = 用户自备服务器**：本应用不提供托管服务，也不内置任何默认地址。约定请求体就是备份包 JSON（`Content-Type: application/json`），**2xx 即成功、不解析响应体**，从而兼容任意自建实现（NAS 脚本、WebDAV 网关、Serverless 函数）。
- **仅 Wi-Fi 用网卡名启发式**：项目未引入 `connectivity_plus`（不为单一开关加依赖），命中 `wlan*`/`wifi*`/`wi-fi*` 视为 Wi-Fi；**探测失败时放行**（宁可上传成功，也不因探测失败静默跳过备份）。

## 新增一个备份项（最小步骤）

1. `BackupItemId` 加枚举值（**发布后不可改名**）。
2. `BackupCatalog.all` 加 `BackupItemSpec`：`title/subtitle/icon/defaultSelected/payloadKey`；分组用 `payloadKey: null` + 子项 `parent:`；含凭据用 `sensitive: true`；有先后依赖用 `requires:`。
3. `backup_collectors.dart` 加 `BackupItemHandler(key: <同 payloadKey>, collect:, apply:)`。
4. 若该项被别的项依赖（或依赖别人），在 `BackupCatalog.applyOrder` 里插入正确位置（不插则排最后）。

完成 1~2 后**自动生效**：UI 复选框（含分组/半选/依赖级联）、包内键名与裁剪、运行日志条目、`BackupRegistry.missing` 校验。缺 handler 的项**不会静默丢数据**：收集时记 `w` 日志「备份项 $key 无实现，跳过」，并在运行日志中标记该项失败。

## 日志规范（TAG = `BACKUP`）

两套日志别混用：

- **调试日志** `AppLogger`（`lib/core/utils/logger.dart`）：release 下静默，TAG 统一 `'BACKUP'`（工具会右对齐到 12 宽，别自造第二 TAG）。`i` = 里程碑（收集完成/上传结果/日志落盘）；`w` = 可恢复异常（回退内存值、未知模块、跳过、探测失败、持久化失败）；`e` = 数据风险（收集/还原失败、回滚失败，带 `StackTrace`）。
- **用户可见运行日志** `BackupLogStore`：落 `app_settings` KV 的独立键 `backup_run_log`（不塞进 `settings_app` 文档，因为日志会持续增长）。每次导出/还原一条 `BackupRunLogEntry`：`id`（时间戳 base36）、`at`、`phase`(export/import)、`trigger`(manual/web/scheduled/legacy)、`keys`、逐项 `BackupItemLog`（`count`/`durationMs`/`error`）、`detail`。环形保留 `maxEntries = 50` 条 + `keepDays` 天（默认 30，0 = 不保留），可导出纯文本 / JSON。
- **禁止**打印鉴权头值、Cookie 明文、令牌。Web 上传日志一律经 `BackupWebClient.redactUrl`（丢掉 query 与 fragment，只留 `scheme://host/path`），令牌放 query 里也不会外泄。

## 定时自动备份（`BackupScheduler` + WorkManager）

`lib/services/backup/backup_scheduler.dart`，单例。由两处驱动：`main.dart` 启动时 `init()` 一次，`SettingsProvider` 在设置变更 / 导入设置后调 `sync()`。

### 两条独立通道：本地与 Web

定时备份有**两条通道**，各有自己的开关与周期，互不依赖：

| | 本地通道 | Web 通道 |
|---|---|---|
| 开关 | `local.enabled` | `webEnabled`（且 `web.usable`） |
| 周期 | `local.schedule` | `web.schedule` |
| 落点 | 应用私有目录 `backups/mtbbs_auto_*.json` | 用户自备服务器的 POST/PUT |
| 需要网络 | 否 | 是（可限仅 Wi-Fi） |
| 典型场景 | 本机留几份、断网也能恢复 | 换机/多设备，服务器当唯一真源 |

**为什么不合成一个开关**：用户可能只想要本机留几份、并不想架服务器；也可能只上传、不想在本机堆文件。合并成一个开关会逼他二选一，还会让「本地有备份」这件事和「有没有服务器」错误绑定。

**但系统里只有一个周期任务**（WorkManager 同名任务只能注册一个），所以：

1. `sync()` 用 `_mergeMinutes` 取两条通道中**较短**的周期来唤醒——取长的会漏跑短周期通道。
2. 每次唤醒后 `runScheduledBackup()` 用 `BackupSchedulePolicy.isDueAt(now)` **各自核对**「距上次执行是否已够一个周期」。没有这一步，短周期通道会把长周期通道一起带成高频执行。
3. 约束取两条通道的**并集**（更严格者胜出）：任一通道要「需充电」，任务就得等充电；任一通道要「仅 Wi-Fi」，就得等 Wi-Fi。放宽任何一条都会让另一条在不符合条件时被白唤醒。
4. **只有 Web 通道需要网络**：本地通道单独开启时 `networkType = NetworkType.notRequired`——断网正是「本机还有备份」最有价值的场景，不该被网络约束挡住。

**只生成一次备份包**：两条通道共用同一份 `ExportToJson` 结果。分别生成会因时间差采集到不同数据（尤其 Cookie 在两次采集之间可能已刷新），而用户看到的「这次备份」应该是同一时刻的快照。

**`force` 绕过到期判断**：用户点「立即备份」时排的是 `registerOneOffTask(inputData: {'force': true})`，后台读到 `force` 就跳过 `isDueAt`。否则刚手动备过、周期未满，点了「立即」却什么都不做。

- **用 WorkManager 而不是 `Timer.periodic`**：用户要的是「一周备份一次」。Timer 只在 App 进程存活时走，手机重启或清理后台之后就不再执行，等于没做。WorkManager 把周期任务注册进系统 JobScheduler，**App 不在前台、进程被杀也会被系统唤起**。
- **周期按「数值 + 单位」存**（`BackupSchedulePolicy.interval/unit`，单位支持分钟/小时/天/周）：让用户自己算 10080 分钟既反人类也容易算错；系统侧统一换算成分钟。
- **15 分钟钳制**：Android 周期任务硬下限是 15 分钟，低于它系统会自动抬到 15。`_effectiveMinutes` 主动做同样的钳制，保证「日志里写的周期」=「系统实际周期」。
- **`sync()` 幂等**：靠 `_registeredMinutes` 与 `_registeredConstraints` 两个指纹比对——周期和约束都没变就直接返回，不重排；变了才 `registerPeriodicTask(existingWorkPolicy: update)`。用 `update` 而非已弃用的 `replace`，能原地改参数而不掐掉正在跑的那次。
- **三个约束条件映射到 WorkManager `Constraints`**：仅 Wi-Fi → `NetworkType.unmetered`（否则 `connected`）、需充电 → `requiresCharging`、电量不低 → `requiresBatteryNotLow`。
- **后台 isolate 必须自己读盘**：每次触发原生侧会新建独立 `FlutterEngine`（见插件 `BackgroundWorker.kt`），主 isolate 的内存状态全部不在。因此 `runScheduledBackup()` 依次做：读 `app_sites` KV 解析成 `List<Site>` → `SettingsRepository.loadAll(hosts)` → `SiteStore.instance.replaceSites(sites)`（**不填则「按站点遍历」的项全是 0 条**）→ 导出 → 上传。
- **结果只能落库，不能回调**：跨 isolate 拿不到主 isolate 的闭包，所以 `_writeBackRunResult` 直接 `SettingsRepository.setApp(...)` 写 `web.lastRunAt/lastResult` 与 `web.schedule.lastRunAt/lastResult`（两处同源写入，避免「页面显示上次时间、实际判断用另一个字段」），主 isolate 下次 `load()` 才看到。
- **失败不重试风暴**：所有「不该跑」的分支（Web 未启用 / 地址无效 / 未开定时 / 未勾任何项）以及异常分支一律 `return true`，把失败交给应用层日志与 UI——用户服务器挂掉时，系统级无限重试只会更糟。退避策略仍配了 `exponential` + 15 分钟起，用于「系统提前终止」这类场景的补偿。
- **能力门控**：`AppCapability.backgroundTask`。`initialize` 抛异常（鸿蒙无实现、插件未注册）即 `disable` 该能力位，UI 隐藏定时入口，手动上传不受影响。
- `runNow(web)` 留作调试：注册一次性任务验证链路，不受周期限制。

## 本地备份存储（`BackupLocalStore`）

`lib/services/backup/backup_local_store.dart`，单例，只管文件系统，不关心备份内容怎么来。

- **落应用私有目录**（`AppPaths.backupsDir` = `{appDataDir}/backups`），不用 `exportsDir`：
  - `exportsDir` 是「用户主动另存为」的兜底落点，混用会让清理旧备份时误删用户手动导出的文件；
  - 后台任务跑在 WorkManager 的独立 isolate，**没有 Activity**，任何 `FileSave`/SAF 选择器都会抛 `MissingPluginException`——私有目录零权限、可直接写；
  - Cookie 是明文凭据，落在私有目录不会被其他应用读到。
- **文件名 `mtbbs_auto_yyyyMMdd_HHmmss.json`**：零填充时间戳让字典序 = 时间序，`list()` 直接按名字倒序就是「最新在前」，不用逐个 stat 比较。
- **`mtbbs_auto_` 前缀隔离归属**：轮转只删带这个前缀的文件。用户自己往 `backups/` 里放的东西不该被自动清理误删。
- **原子落盘**：先写 `xxx.json.tmp` 再 `rename`。中途被杀进程不会留下半截 JSON——而半截 JSON 在列表里看起来像个正常备份，点进去才报解析失败。
- **轮转**：`_rotate` 按份数删最旧的（`files.skip(keepCount)`）；`keepCount <= 0` 视为「不清理」，用户显式选择全部保留。单个删除失败只记 `w` 日志，不中断——本次备份已经成功，不该因为删不掉旧文件而报失败。
- **大小显示**：`LocalBackupFile.sizeLabel` 在模型上，UI 不重复实现。

备份页的「本机备份文件」入口可列 / 读 / 删 / 恢复。恢复走与「从文件恢复」**完全相同**的 `_importText` 流程（敏感项确认 → 模块挑选 → 合并/覆盖 → 逐项或事务式），只是文本来源换成私有目录里的文件。两套导入流程迟早会在某个校验上分叉，所以只留一个。

## 与上游仓库的兼容
本 fork 的备份系统与上游 `qcxs/mtbbs_app` 的备份能力是**两套并存**的东西，不要互相替代：

| | 上游 `DataPortability` | 本 fork `BackupService` |
|---|---|---|
| 文件 | `lib/services/data_portability.dart` | `lib/services/backup/*` |
| 入口 | 上游在 `lib/pages/settings/about_page_data.dart`（本 fork 已删除该页）；本 fork 在 `/settings/backup` 的「账号 Cookie」区块重建了同等入口 | `/settings/backup` 页 |
| 格式 | `mtbbs.settings` v1（`{format, version, exportedAt, app, sites}`）+ `mtbbs.cookies` v1 | `mtbbs.backup` v2，可勾选的模块化包 |
| 粒度 | 全量，不能选 | 按 `BackupItemId` 逐项勾选 |
| 能力 | 导出/导入设置与 Cookie | 收集/应用 + Web 上传 + 定时调度 + 运行日志 |

**上游那套一直在仓库里**，本 fork 并没有删掉它：`backup_collectors.dart` 里「账号列表」与「Cookie」两项都是直接调 `DataPortability.exportCookiesJson/importCookiesJson` 实现的，备份页的「导出 / 导入账号 Cookie」也是。所以「兼容上游」的含义是：**上游的导出文件本 fork 能导入，本 fork 的导出文件上游能导入**，而不是重写一套。

「导入账号 Cookie」接受两种输入：独立的 `mtbbs.cookies` v1 文件，或含 `cookies` 模块的 `mtbbs.backup` v2 包（取 `modules['cookies']` 本体再交给同一个导入器）。所以用户不必记住自己手上是哪种文件。

导入兼容靠 `backup_pack.dart` 的格式识别：读到的 JSON 若 `format` 是 `mtbbs.settings` 或 `mtbbs.cookies`，按旧格式转换成本 fork 的 `mtbbs.backup` v2 结构再走正常应用流程。**新增备份项时不要动这层识别逻辑**，否则老文件会全部失效。

### `AppSettings.backup` → 独立 KV 键 `backupSettings`
上游的 `AppSettings` 没有 `backup` 字段，本 fork 之前把备份配置塞进了它。这带来两个问题：

1. **合并冲突**：`app_settings.dart` 的 import / 构造参数 / `toMap` / `fromMap` / `copyWith` 五处都被改动，上游每次改这个文件都要手工解冲突。
2. **耦合**：备份配置与「应用设置」是不同生命周期的东西，混在一起会让 `settings_app` 文档越来越胖。

改造后：
- 新增 `lib/services/backup/backup_settings_store.dart`，`BackupSettingsStore.instance`，KV 键 `backupSettings`，提供 `load()` / `save()` / `update()` / `current`。
- `load()` 内含**惰性迁移**：`backupSettings` 为空时读 `app_settings` 文档里的旧字段 `backup`，搬到新键后把该字段从文档里移除。
- `AppSettings` 恢复成与上游同构的形态（不含 `backup`），此后上游改这个文件不再产生冲突。
- `backup_collectors.dart` 的「应用设置」项收集时 `map.remove('backup')`，应用时同理——**旧备份包里带的 `backup` 字段直接丢弃**，不写回 `app_settings`；备份配置本身由 `backupSettings` 键独立备份。

**约定**：fork 专属配置一律走独立 KV 键（`commentFilter`、`threadScopeFilter_*`、`backupSettings` 都是这个范式），**不要往 `AppSettings` / `Site` 这类与上游共享的模型里加字段**。共享模型只留上游已有的字段，fork 的新增配置另开键，这样上游合并时这些文件可以整体取上游版本。

## 凭据存储（`SecretStore`）

- `SecretStoreMode{plain, secure}`，UI 里让用户自己选：**明文**（随 `settings_app` 文档，简单、可导出）或 **密钥库**（`flutter_secure_storage`，Android 走 `encryptedSharedPreferences: true`）。
- `lib/platform/optional/secure_store.dart` 是**唯一** import `flutter_secure_storage` 的地方，属「可选平台能力」层；`MissingPluginException` / `PlatformException` 一律降级并记 `w` 日志，同时 `AppCapabilities.disable(secureStore)`。
- 键前缀 `mtbbs.backup.secret.`，Web 备份鉴权值键名 `web_backup_auth`（`BackupWebClient.secretKey`）。
- `WebBackupConfig.toMap()` 在 secure 模式把 `headerValue` 写成空串——避免「以为加密了，其实文档里还留了一份明文」。
- `setWebBackupSecretMode` 双向搬值：转 secure 时写密钥库并清空明文字段；转 plain 时把密钥库值搬回文档并删除密钥库副本。转 secure 前先查 `SecretStore.available`，不可用则返回 false 且不改设置。

## 已落地（本轮）
- 设置页三件套：`backup_page.dart`（备份项复选框 + 本地备份 + 账号 Cookie + Web 配置 + 定时策略 + 立即上传）、`backup_log_page.dart`（日志查看与导出）。
- **本地自动备份**：`BackupLocalConfig`（开关 / 保留份数 / 周期 / 上次结果）+ `BackupLocalStore`（私有目录、原子落盘、按份数轮转）+ 备份页「本地备份」区块（立即备份 / 文件列表 / 恢复 / 删除）。
- **Cookie 单独备份**：`BackupItemId.cookies` 从 `accountCookies` 拆出；备份页新增「账号 Cookie」区块，提供与上游一致的「导出 / 导入账号 Cookie」（`mtbbs.cookies` v1）。
- **双通道调度**：`BackupScheduler` 同时服务本地与 Web，系统里只注册一个周期任务，按较短周期唤醒、各自用 `isDueAt` 判断到期；本地单独开启时不等网络。
- Web 定时调度：`BackupScheduler`（见上节），系统级，App 关闭也会执行。
- 鉴权值可选加密存储（见上节）。
- URL 脱敏：`BackupWebClient.redactUrl` 丢掉 query 与 fragment，日志只留 `scheme://host/path`，令牌放 query 也不会外泄。
- `CHANGELOG.md` 与本文档同源维护，发版按版本号追加小节。
